# M1 — 행정동 신·구 코드 매핑 (`data/processed/adm_code_map.csv`)

작성일: 2026-08-22
작성자: Claude Code
근거: `reports/m0_data_audit.md` 2번 항목, `reports/m1_structure_proposal.md` 2번 항목

## 배경

M0 감사에서 KOSIS `DT_216N_B000J2`의 objL1(행정구역별) 코드에 죽도동/죽도1동·2동, 해도동/해도1동·2동, 상대동/상대1동·2동이 동시에 존재하는 걸 확인했지만, SGIS API 키가 없어 "어느 쪽이 현재 유효한 행정동인가"는 미해결로 남겨뒀다. 이번 문서는 **SGIS 경계 파일 없이도** 확인 가능한 부분 — 행정안전부 행정구역 개편 이력 — 을 위키백과 교차 확인으로 먼저 닫은 결과다.

## 방법

1. `kosis_table_info(type=ITM, objId=15216A11)`로 포항시 산하 objL1 코드 전체(39건: 포항시 자체 1 + 남구/북구 2 + 읍면동 36)를 조회.
2. 위키백과 "포항시의 행정 구역" 문서 + 개별 동 문서(죽도동, 중앙동(포항시), 학산동(포항) 등)로 각 코드의 통합·분동 연혁을 교차 확인.
3. 두 결과가 일치하는지 대조 — KOSIS에 남아있는 옛 코드(학산동, 상대1·2동, 해도1·2동, 죽도1·2동) 전부가 위키백과 통합 이력과 정확히 대응됨을 확인.

## 핵심 발견

**현재 유효한 포항시 읍면동은 29개다** (4읍 + 10면 + 15행정동): 이전 M0 문서가 "36개"로 집계했던 건 폐지된 옛 코드(학산동, 상대1·2동, 해도1·2동, 죽도1·2동 = 7개)를 현재 코드와 함께 셌기 때문이다. `config/pipeline.yaml`의 대상 행정동 목록은 이 29개만 써야 한다 — 옛 코드까지 넣으면 인구·시설 데이터가 이중 집계된다.

**구(區) 소속이 바뀐 사례가 있다 — 이름만 다른 게 아니다.** KOSIS의 옛 코드 계층상 상대1동·상대2동·해도1동·해도2동은 **북구** 하위로 기록돼 있는데, 2009-01-01 통합 이후의 상대동·해도동은 **남구** 소속이다. 단순 문자열 매핑(옛 이름→새 이름)만으로는 이 구 소속 변경을 놓치기 쉽다. `admin_join.py`나 `config/pipeline.yaml`에서 구 단위로 뭔가를 집계·필터링한다면 이 표의 `gu` 컬럼(현재 기준)을 반드시 참조해야 한다.

**죽도동은 반복 분동·통합 이력이 있다.** 1961→1966, 1970→2009 두 번 분동됐다가 재통합됐다. 시계열을 다룰 때 죽도동/죽도1·2동을 하나로 이어붙이면 안 되고, 2009년 이전 시점 데이터가 필요하면 이 반복 이력을 감안해야 한다.

## 파일 형식

`data/processed/adm_code_map.csv` — 컬럼: `adm_cd_kosis`(KOSIS objL1 코드), `adm_nm`(이름), `gu`(현재 기준 소속 구), `status`(current/deprecated), `current_adm_cd_kosis`/`current_adm_nm`(현재 유효 코드로 매핑), `merged_date`, `note`(연혁·주의사항).

## 남은 한계

- **SGIS 경계 폴리곤과의 코드 대조는 여전히 안 됨.** 이 문서는 KOSIS 코드 체계 내부의 신·구 매핑만 닫은 것이고, SGIS Open API 키를 발급받아 실제 경계 SHP 파일의 행정동 코드가 이 표와 일치하는지는 별도로 검증해야 한다(M1 구조제안 문서의 원래 액션 아이템 그대로 유효).
- 이 표는 KOSIS `DT_216N_B000J2`의 objL1 코드 체계 기준이다. 심평원 병원/약국 데이터의 `읍면동` 컬럼은 원문 텍스트(예: "죽도동")라 이름 매칭만으로는 옛 코드 문제가 발생하지 않지만, 좌표 기반 point-in-polygon 매칭을 쓸 때는 SGIS 경계 파일의 코드 체계와 이 표를 함께 대조해야 한다.

## 부수 수정 — `Data/` → `data/raw/` 폴더 이동

작업 중 발견: 이 프로젝트가 있는 macOS 볼륨은 대소문자를 구분하지 않는 파일시스템(APFS)이라, 기존 최상위 `Data/`(원본 데이터, gitignore 대상)와 README가 계획한 `data/processed/`가 **같은 폴더**로 취급된다(`ls -id Data`와 `ls -id data`가 동일 inode 반환 확인). 그대로 두면 `data/processed/`에 커밋용 파일을 만들어도 실제로는 `Data/`(gitignore 대상) 안에 들어가 버려 영영 안 잡힌다. 원본 데이터 두 파일을 `data/raw/`로 옮기고 `.gitignore`의 `Data/` 항목을 제거했다(이미 있던 `data/raw/` 항목만 남김) — README가 원래 계획한 구조와도 일치한다. 원본 데이터는 아직 git에 안 잡혀있던 상태라 이동 자체는 안전했다.
